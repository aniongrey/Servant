# 会议、Galgame 与桌面语音归属

## 本次已实现

- 正常启动先打开 meeting；首次使用仍先完成初始化，完成后进入 meeting。
- meeting 的 React 界面和舞台命令监听挂载后通知 Tauri，再按原窗口配置创建 desktop；不再自动打开 chat，也不使用固定延时。
- `src/ai/tts/characterVoiceConfig.ts` 统一解析角色音色：未绑定音色沿用用户的全局选择；绑定音色使用所属供应商的完整配置；绑定已失效则禁用该角色 TTS 并记录错误，不偷偷换成 Windows 语音。

用户反馈的是 Windows 声音与角色声音同时出现。当前 meeting 只发送 `action.voice`，Galgame 不直接合成语音，播放入口在 desktop。原先广播允许每个 desktop renderer 独立朗读同一事件；现由 `listenVoicePlayback` 在播放前向网关领取 `(turnId, characterId)` 的唯一播放权，其余窗口仍可观察气泡与状态，但不能重复朗读。等待授权期间缓存片段，重复开始事件忽略，断线取消本地播放。网关保留最近 2048 轮的领取记录，断线后不转让旧句子以免重播；新轮次可以由其他播放端领取。

回归测试同时接入 Windows 和角色 TTS 两个播放端，验证单次朗读、分段顺序、重复事件与下一轮 Windows 正常朗读；另用两个真实 WebSocket 连接验证原子领取。尚未在用户当前运行的 WebView 中实测听音，更新后需要重启应用及后端。

## 推荐归属

将语音运行时独立为 `src/ai/tts/CharacterVoiceRuntime.ts`，复用现有 `TtsManager`、`SpeechController` 和各 Provider，不另起后端进程。它的生命周期由应用管理，与某个 VRM 模型是否显示解耦。

| 模块 | 职责 |
| --- | --- |
| meeting | 发言顺序、用户输入、生成回复、取消轮次；不创建播放器 |
| chat | 显示聊天记录、提交请求、消费播放状态；不创建播放器 |
| CharacterVoiceRuntime | 角色音色解析、合成预取、唯一播放队列、取消、错误与完成回执 |
| desktop / Galgame | 渲染角色，按实际播放时刻驱动口型、表情和动作；切换视图不重建播放器 |
| `src/ai/stt/` | 麦克风和识别；保留现有独立边界，不与 TTS 生命周期捆绑 |
| 后端 | 对话编排、供应商请求和实时消息路由；不承担浏览器音频播放 |

应用只启动一个语音宿主。先在 desktop 内挂载独立运行时；只有确实需要关闭 desktop 后继续有声对话时，再迁到独立隐藏 WebView。不要放到 meeting 组件内部，否则会议页重载或关闭会截断播放。Windows 系统语音保留为明确选择的 Provider，不用作其他 Provider 失败后的隐式兜底。

## 实施顺序与验收

1. 复现并定位重叠：按 `turnId / characterId / providerId / renderer` 记录开始、结束、取消。确认是同一台词重复还是不同角色抢话，避免直接禁用 Microsoft 掩盖问题。
2. 抽出播放运行时：把 `DesktopPet` 的语音订阅、角色路由和待播缓冲移出 UI；模型注册只提供动作与口型适配。角色移出画面不触发另一条语音链。
3. 保证单一播放所有者：由网关按会话登记语音宿主并定向发送；额外窗口仅接收状态。同一轮次和片段只消费一次，宿主断线释放所有权，未完成台词不自动重播。
4. 完成/失败/取消回执分开：会议队列以真实播放结束推进。角色配置缺失、合成失败或播放超时显示可定位的错误，不伪装成正常完成。
5. 验收会议单独使用、会议 + Galgame、多窗口、模式切换、打断、供应商切换、角色隐藏、宿主关闭重开。每段台词最多一个实际播放者；口型与声音同步；错误路径无 Windows 兜底声。

已完成第 3 步的逐轮唯一播放权，不需要迁移现有播放器。独立语音宿主、完整失败回执及全场景验收仍是后续计划。
